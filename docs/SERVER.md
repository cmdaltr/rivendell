# Rivendell as a team server

One Rivendell on a central host, used by a DFIR team through their browsers or the desktop app's "connect to a server" mode. The evidence stays on the server's storage, the heavy tools (Volatility, Plaso, ClamAV, Ollama for Eru) run on one well-specified box, and cases live in one place, with one audit trail.

A local install (an analyst's own machine, the lab) is unchanged. Everything here switches on with `rivendell server init`.

## What changes on a server

| | Local | Server |
|---|---|---|
| Network | Every service's port published | Caddy only: 443 (and 80 for redirects and ACME); Splunk, Kibana and the Navigator on 7755, 5601 and 5602 through Caddy, behind the Rivendell sign-in |
| TLS | None | Caddy: its own CA, Let's Encrypt, or your organisation's certificate |
| Sign-in | Optional; guest access; open sign-up | Required for every API route; no guests; admins create accounts; single sign-on (OIDC) optional |
| Jobs | Everyone sees everything | Each job is visible to its owner, the users it's shared with, and admins |
| Eru | Every case | The cases behind jobs you can see |
| Admin areas | — | Lab, Andúril and Mordor downloads are admin-only |
| Frontend | Development server | Production build (nginx), same origin as the API |
| Secrets | Built-in defaults | Generated by `server init`; the stack refuses to start without them |

Server mode is the backend setting `RIVENDELL_SERVER_MODE`, which `deploy/server/docker-compose.server.yml` sets. The checks live in one middleware (`src/web/backend/auth/access.py`), so a route added later is covered without remembering to protect it.

## Setting up

Requirements: a Linux host with Docker Engine and Compose 2.24 or later, and a DNS name for it. Ubuntu 24.04 with Docker's own packages is the tested shape.

```bash
git clone https://github.com/cmdaltr/rivendell.git && cd rivendell
./rivendell install
rivendell server init rivendell.dfir.example.org
rivendell start
```

`server init` writes the server settings into `.env` (mode 600): the hostname, the certificate choice, a random `SECRET_KEY`, the first admin's password (printed once), and random Postgres, Elastic and Splunk passwords for stores that don't exist yet. Run it again to change the hostname or certificate; secrets already set are kept. From then on, `rivendell start`, `stop` and `status` use the server profile without being asked (`--server` forces it).

With Splunk, Elastic and the Navigator:

```bash
COMPOSE_PROFILES=siem rivendell start
```

Sign in at `https://rivendell.dfir.example.org` as `admin` with the printed password, and change it under Account.

### Certificates

| `--tls` | Certificate | Clients |
|---|---|---|
| `internal` (default) | Caddy's own CA | Trust its root: `rivendell server ca > rivendell-root.crt`, then distribute it (MDM, Group Policy, `update-ca-certificates`) |
| `you@example.org` | Let's Encrypt | Nothing to do; the name must reach the host on 80 and 443 |
| `files` | `deploy/server/certs/rivendell.crt` and `rivendell.key` (your PKI) | Whatever already trusts your PKI |

### Evidence

Paths in Rivendell are paths on the server. Mount your evidence storage on the host and make it visible to the containers with a `docker-compose.local.yml` beside `docker-compose.yml` (the launcher adds it when it exists; it's gitignored):

```yaml
services:
  backend:
    volumes:
      - type: bind
        source: /srv/evidence
        target: /mnt/evidence
        read_only: true
  celery-worker:
    volumes:
      - type: bind
        source: /srv/evidence
        target: /mnt/evidence
```

Mount it under `/mnt` or `/media` inside the containers: those (and `/tmp/rivendell`) are the only places the file browser and job creation accept on Linux. Gandalf archives copied to that share are picked up like any other source.

## Users

```bash
rivendell server users list
rivendell server users add alice alice@example.org            # prompts for a password
rivendell server users add bob bob@example.org --admin
rivendell server users role alice admin
rivendell server users disable bob
rivendell server users password admin                          # a locked-out admin
```

These work inside the backend container, so they work when nobody can sign in. Admins can do the same through the API (`/api/auth/users`). Passwords on a server need at least 12 characters, and five failed sign-ins lock a username for 15 minutes (`max_login_attempts`, `lockout_duration_minutes`).

### Single sign-on

Register Rivendell with your identity provider as a confidential web application:

| Setting | Value |
|---|---|
| Redirect URI | `https://<hostname>/api/auth/oidc/callback` |
| Grant | Authorization code (Rivendell uses PKCE) |
| Scopes | `openid profile email` |
| Claims | A groups claim, if roles should follow groups |

Then add to `.env` and restart:

```bash
OIDC_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0
OIDC_CLIENT_ID=...
OIDC_CLIENT_SECRET=...
OIDC_DISPLAY_NAME=Microsoft          # the button says "Sign in with Microsoft"
OIDC_ADMIN_GROUP=<group id or name>  # members become Rivendell admins; others are users
OIDC_ALLOWED_GROUP=<group>           # optional: only members (and admins) may sign in
RIVENDELL_LOCAL_LOGIN=false          # optional: SSO only; admins keep a password as break-glass
```

The ID token is verified against the issuer's published keys, its audience and the sign-in's nonce. Users are matched on issuer and subject, so a renamed account stays the same Rivendell user; the first sign-in creates them. With `OIDC_ADMIN_GROUP` set, the role follows the group at every sign-in. Entra ID puts group object IDs in the `groups` claim (enable it under Token configuration); Okta and Keycloak need a groups claim mapper.

## Sharing jobs

A job belongs to the user who created it. On its page, the Access panel shows the owner and who it's shared with; the owner or an admin adds and removes people. The people it's shared with can see and work on it (cancel, restart, export, ask Eru), but can't reshare it. Jobs created before the server existed have no owner: admins see them and can share them.

Case numbers name output directories, so they're unique across the server: creating a job with a case number someone else used is reported as a clash, without showing their job.

## The desktop app

People can use the server from the desktop app instead of a browser tab: in setup, choose **Connect to my team's Rivendell server** and enter the hostname. Nothing runs locally: no Docker, no files. The Mac app needs the server's certificate to be trusted by the Mac (Keychain); the Linux and Windows apps open it in an Edge or Chromium app window. See `app/README.md`.

## Limits worth knowing

- **Andúril holds the Docker socket.** It's opt-in (`rivendell anduril enable`) and admin-only on a server, but whoever administers it administers the host's Docker.
- **The Navigator's layers** (one per case, named after the case) are readable by any signed-in user who knows the case name. Splunk and Kibana have their own users and indexes; Rivendell's sign-in in front of them doesn't map its job sharing onto them.
- **One backend process.** Sign-in lockouts are counted in memory, so a restart resets them.
- **Sessions are 24-hour tokens** (`access_token_expire_minutes`); disabling a user stops their next request, since every request checks the user store.
- **The schema.** Ownership lives in a `job_access` table beside `jobs`, created on start like `jobs` itself, with an Alembic migration (`b7e4c2d9a810`) for databases managed through Alembic.
